<objective>
Shrink the signed feedback token so Brevo-wrapped star links (`/feedback?r=N&t=TOKEN&s=2`) stay well under the 2083-char limit some mail clients enforce. Today the full LetterDebugPayload (~970 bytes JSON) is base64url'd uncompressed; Brevo click tracking (cannot be disabled for transactional mails) turns that into ~2090-2128-char URLs, some clients truncate them, Brevo answers 404 and the rating is lost.

Purpose: no more lost star ratings from truncated links, without dropping any payload field (reviews.debug_payload stores the full payload) and without breaking tokens in mails that are already in inboxes.

Output: `web/src/lib/feedback/token.ts` compresses with deflateRaw (level 9) behind an explicit `z` format prefix and verifies both formats; new `web/src/__tests__/feedbackToken.test.ts` proves roundtrip, legacy compatibility, size win and rejection cases.

Format decision (planner's discretion, no CONTEXT.md decisions exist for this quick task): explicit one-char prefix `z` instead of sniffing "starts with eyJ". Reason: a raw deflate stream with a fixed-Huffman final block can begin with byte 0x7B, whose base64 also starts with `e`, so "not eyJ means compressed" is only probabilistically safe. A legacy body always starts with `e` because `JSON.stringify` of an object starts with `{`, so `z` can never be a legacy body. The prefix sits inside the MAC'd body, so nobody can flip the mode without the secret.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mail link / browser -> /feedback page, submitReview action, /api/review-improvement-click | The `t` token is attacker-controllable input; only the HMAC with FEEDBACK_TOKEN_SECRET makes it trustworthy |
| Brevo click tracking -> user's mail client | Brevo rewraps the link; length decides whether the click reaches us at all |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-qg2-01 | Denial of Service | verifyFeedbackToken inflate step | medium | mitigate | MAC is verified with timingSafeEqual before any decode or inflate, so only secret holders can submit a compressed body; inflateRawSync additionally gets maxOutputLength 64 KiB and its RangeError is swallowed by the existing try/catch (Task 2 bomb test). Input size is already capped at 4000 chars by the zod schemas in submitReview and review-improvement-click |
| T-qg2-02 | Tampering | format prefix `z` vs legacy body | medium | mitigate | The prefix is part of the MAC'd body string, so switching between compressed and legacy decoding requires the secret; legacy bodies always start with `e`, so a genuine legacy token can never be misread as compressed (Task 1 legacy test, Task 2 tamper tests) |
| T-qg2-03 | Repudiation / Availability | star links in mails already sent | high | mitigate | Legacy uncompressed tokens (incl. tokens from web/scripts signers) keep verifying through the unchanged legacy branch; covered by the Task 1 legacy test. Without this, every rating from older mails would be rejected as invalid_token |
| T-qg2-04 | Information Disclosure | token payload (userEmail, plz) | low | accept | Compression is encoding, not encryption; the payload was readable base64 before and stays equally readable. Keeping userEmail and plz in the link is an existing, documented decision (2026-05-27); no new data enters the token. No compression oracle: the body holds no secret, the MAC is computed after compression |
| T-qg2-SC | Tampering | npm/pip/cargo installs | high | accept | No package installs in this plan; node:zlib is a Node built-in, so the package-legitimacy gate has nothing to check |
</threat_model>
